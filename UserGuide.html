AvengerHub User Guide

AvengerHub is a desktop address book application for managing students, optimized for use through a Command Line Interface (CLI) while retaining the benefits of a Graphical User Interface (GUI). If you type quickly, AvengerHub can help you manage students faster than traditional GUI applications.

Quick start

  1. Ensure that Java 25 or later is installed on your computer.
    Mac users: Ensure you have the precise JDK version prescribed here.

  2. Download the latest .jar file from here.

  3. Copy the file to the folder you want to use as the home folder for your AvengerHub.

  4. Open a terminal, cd to the folder containing the JAR file, and run java -jar avengerhub.jar.
    A GUI similar to the one below should appear in a few seconds. Note how the app contains some sample data in its address book.

  5. Type a command in the command box and press Enter to execute it. For example, type help and press Enter to open the help window.
    Some example commands you can try:

    • list : Lists all students.

    • addstudent n/John Doe p/98765432 e/johnd@example.com g/1A : Adds a student named John Doe to the Address Book.

    • delstudent id/3 : Deletes the 3rd student shown in the current list.

    • clear : Deletes all students.

    • exit : Exits the app.

  6. Refer to the Features section below for details of each command.

Features

Notes about the command format:

  • Words in UPPER_CASE are the parameters to be supplied by the user.
    For example, in addstudent n/NAME, replace NAME with a value such as John Doe.

  • Items in square brackets are optional.
    For example, n/NAME [t/TAG] can be used as n/John Doe t/friend or as n/John Doe.

  • Items followed by ... can appear zero or more times.
    For example, [t/TAG]... may be omitted, or written as t/friend or t/friend t/family.

  • Prefixed parameters can be in any order unless a command states otherwise.
    For example, if the command specifies n/NAME p/PHONE_NUMBER, p/PHONE_NUMBER n/NAME is also acceptable.

  • Prefixes are case-insensitive.
    For example, n/John Doe and N/John Doe both specify the same name parameter.

  • Commands that take no parameters ignore extra arguments.
    The list command displays a warning when extra arguments are ignored. The other commands ignore extra arguments without a warning.
    For example, help 123 is interpreted as help without a warning.

  • If you are using a PDF version of this document, be careful when copying and pasting commands that span multiple lines as space characters surrounding line-breaks may be omitted when copied over to the application.

Viewing help: help

Opens the help window containing usage instructions for the commands.

Format: help

Adding a student: addstudent

Adds a student to the address book.

Format: addstudent n/NAME p/PHONE_NUMBER e/EMAIL [t/TAG]... g/STUDIO_GROUP

Tip: A student can have any number of tags, including zero.

Examples:

  • addstudent n/John Doe p/98765432 e/johnd@example.com g/1A
  • addstudent n/Betsy Crowe t/talkative e/betsycrowe@example.com p/1234567 t/smart g/1A

Listing all students: list

Shows a list of all students in the address book.

Format: list

  • Resets the current student filter to show all students.
  • Extra arguments are ignored with a warning; the command still lists all students.
  • Surrounding whitespace does not trigger a warning.

For example, list missions m/01 lists all students and displays:

Listed all students.
WARNING:
Extra arguments were ignored. The list command takes no arguments.

To list mission submissions, use listmissions m/M01.

Viewing a student: view

Displays the profile of a student in the currently displayed student list.

Format: view id/INDEX

  • INDEX refers to the student's index in the currently displayed list, including results from find.
  • The index must be a positive integer identifying a displayed student.
  • The profile displays the student's name, studio group, phone number, email address, tags, studio records, missions, mastery checks, and notes.
  • Mission statuses are Submitted or Not submitted, based on the records maintained in AvengerHub.
  • An empty mission catalogue displays No missions configured.
  • Viewing preserves student records, submission records, and the current filter.
  • Missing, invalid, or out-of-range indexes produce an error without changing stored records.

Examples:

  • list, followed by view id/2, displays the second student's profile.
  • find Betsy Crowe, followed by view id/1, displays the first student in those search results.

For example, viewing Amy Lee displays the feedback:

Showing profile of Amy Lee

Editing a student: editstudent

Edits an existing student in the address book.

Format: editstudent id/INDEX [n/NAME] [p/PHONE] [e/EMAIL] [t/TAG]... [g/STUDIO_GROUP]

  • Edits the student at the specified INDEX. The index refers to the index number shown in the displayed student list. The index must be a positive integer 1, 2, 3, ...
  • At least one of the optional fields must be provided.
  • Existing values will be updated to the input values.
  • When editing tags, all of the student's existing tags are removed; adding tags is not cumulative.
  • To remove all of a student's tags, enter t/ without a tag after it.

Examples:

  • editstudent id/1 p/91234567 e/johndoe@example.com Edits the phone number and email address of the 1st student to be 91234567 and johndoe@example.com respectively.
  • editstudent id/2 n/Betsy Crower t/ Edits the name of the 2nd student to be Betsy Crower and clears all existing tags.

Locating students by name: find

Finds students whose names contain any of the given keywords.

Format: find [NAME_WORDS [, MORE_NAME_WORDS]...] [g/STUDIO_GROUP]...

  • Provide at least one name alternative or studio group.
  • Name matching is case-insensitive and allows partial matches.
  • Spaces mean AND: alex lee requires both words, in any order.
  • Repeating a word within an alternative requires separate, non-overlapping occurrences, ignoring case. For example, alex alex matches Alex Alex and Alex Alexander, but not Alex Yeoh.
  • Comma-separated alternatives are independent: alex, alex has the same effect as alex.
  • Commas mean OR: alex lee, brian matches both alex and lee, or matches brian.
  • Spaces around commas are optional.
  • Empty alternatives are invalid: do not begin or end the name search with a comma, or use consecutive commas.
  • Studio groups match exactly.
  • Repeated group filters mean OR: g/1A g/1B matches either group.
  • When names and groups are supplied, both filters must match.
  • Place name alternatives before studio-group filters.

Examples:

  • find ale lee matches Alex Lee, but not Alex Lim.
  • find alex, david matches Alex Lee and David Li.
  • find alex, brian g/1A matches Alex or Brian within studio group 1A.
  • find g/1A g/1B finds students in either studio group.

Deleting a student: delstudent

Deletes the specified student from the address book.

Format: delstudent id/INDEX

  • Deletes the student at the specified INDEX.
  • The index refers to the index number shown in the displayed student list.
  • The index must be a positive integer 1, 2, 3, ...

Examples:

  • list followed by delstudent id/2 deletes the 2nd student in the address book.
  • find Betsy followed by delstudent id/1 deletes the 1st student in the results of the find command.

Adding studio records: addstudiorecord

Records a student's studio attendance and effort for a studio week.

Format: addstudiorecord id/INDEX w/WEEK ef/EFFORT

  • Adds a studio record for the student at the specified INDEX for the specified WEEK, with the specified EFFORT score.
  • The index refers to the index number shown in the displayed student list.
  • The index must be a positive integer 1, 2, 3, ...
  • The week must be an integer from 0 to 13, inclusive.
  • The effort score must be a whole number from 0 to 2147483647, inclusive.
  • Weeks without a record shown are considered absent with an effort score of 0.
  • If the studio record was already recorded, the records remain unchanged.
  • The current list filter stays active.

Examples:

  • list followed by addstudiorecord id/1 w/3 ef/30 records attendance and an effort score of 30 for week 3 for the first student displayed, if any.
  • find Betsy followed by addstudiorecord id/1 w/13 ef/0 records attendance and an effort score of 0 for week 13 for the first student in the search results, if any.

For example, if the first student is Amy Bee and her week 3 studio record is not yet recorded, addstudiorecord id/1 w/3 ef/30 displays:

Added Amy Bee's studio record for studio week 3.

Deleting studio records: delstudiorecord

Removes a student's attendance record and effort score for a studio week. The student remains in the address book.

Format: delstudiorecord id/INDEX w/WEEK

  • Deletes a studio record for the student at the specified INDEX for the specified WEEK.
  • The index refers to the index number shown in the displayed student list.
  • The index must be a positive integer 1, 2, 3, ...
  • The week must be an integer from 0 to 13, inclusive.
  • If the studio record was already not recorded, the records remain unchanged.
  • The current list filter stays active.

Examples:

  • list followed by delstudiorecord id/1 w/3 removes the first student's week 3 studio record, if recorded, if any.
  • find Betsy followed by delstudiorecord id/1 w/13 removes the week 13 studio record for the first student in the search results, if any.

For example, if the first student is Amy Bee and her week 3 studio record is recorded, delstudiorecord id/1 w/3 displays:

Removed Amy Bee's record for studio week 3.

Editing studio records: editstudiorecord

Edit a student's studio effort for a studio week.

Format: editstudiorecord id/INDEX w/WEEK ef/EFFORT

  • Edits a studio record for the student at the specified INDEX for the specified WEEK, with the specified EFFORT score.
  • The index refers to the index number shown in the displayed student list.
  • The index must be a positive integer 1, 2, 3, ...
  • The week must be an integer from 0 to 13, inclusive.
  • The effort score must be a whole number from 0 to 2147483647, inclusive.
  • If the studio record was already not recorded, the records remain unchanged.
  • If the studio record's existing effort score is the same as the specified effort score, the records remain unchanged.
  • The current list filter stays active.

Examples:

  • list followed by editstudiorecord id/1 w/3 ef/30 edits studio record's effort score to 30 for week 3 for the first student displayed, if any.
  • find Betsy followed by editstudiorecord id/1 w/13 ef/0 edits studio's effort score to 0 for week 13 for the first student in the search results, if any.

For example, if the first student is Amy Bee and her week 3 studio record is recorded, editstudiorecord id/1 w/3 ef/30 displays:

Edited Amy Bee's studio record for studio week 3.

Adding a student note: addnote

Adds a note for an existing student in the address book.

Format: addnote id/INDEX nt/TEXT

  • Adds a note with text TEXT for the student at the specified INDEX.
  • The index refers to the index number shown in the displayed student list.
  • The index must be a positive integer 1, 2, 3, ...
  • The text should only contain alphanumeric characters and spaces, should not be blank, and be less than or equal to 100 characters.
  • A student can have up to 10 notes.
  • The current list filter stays active.

Examples:

  • addnote id/1 nt/hello Adds a note with text hello for the 1st student.

Deleting a student note: delnote

Deletes a note for an existing student in the address book.

Format: delnote id/INDEX ni/NOTE_INDEX

  • Deletes a note with index NOTE_INDEX for the student at the specified INDEX.
  • The index refers to the index number shown in the displayed student list.
  • The index must be a positive integer 1, 2, 3, ...
  • The note index refers to the index number shown in the list of notes for a given student in the display panel.
  • The note index must be an integer from 1 to 10, inclusive.
  • If the note index doesn't match any existing notes for the given student, the notes will be unchanged.
  • The current list filter stays active.

Examples:

  • delnote id/1 ni/1 Deletes the first note for the 1st student.

Editing a student note: editnote

Edits a note for an existing student in the address book.

Format: editnote id/INDEX ni/NOTE_INDEX nt/TEXT

  • Edits a note with index NOTE_INDEX, replacing its text with TEXT for the student at the specified INDEX.
  • The index refers to the index number shown in the displayed student list.
  • The index must be a positive integer 1, 2, 3, ...
  • The note index refers to the index number shown in the list of notes for a given student in the display panel.
  • The note index must be an integer from 1 to 10, inclusive.
  • The text should only contain alphanumeric characters and spaces, should not be blank, and be less than or equal to 100 characters.
  • If the note index doesn't match any existing notes for the given student, or matches the existing text, the notes will be unchanged.
  • The current list filter stays active.

Examples:

  • editnote id/1 ni/1 nt/hello Edits the first note, replacing its text with hello for the 1st student.

Adding a mastery check: addmc

Adds a numbered mastery check appointment for a student.

Format: addmc id/INDEX num/NUMBER dt/DATE-TIME

  • INDEX must be a positive integer identifying a student in the currently displayed list, including find results.
  • NUMBER must be an integer from 1 to 2147483647, inclusive. Numbers are unique within each student's appointments.
  • DATE-TIME must be a real date and 24-hour time in dd-MM|HH:mm format, such as 29-10|13:30. The current year is filled in automatically. Impossible dates, 24:00, and times with seconds are rejected.
  • Supply id/, num/, and dt/ exactly once each, in any letter case and in any order. Do not put text before the first prefix.
  • New mastery checks show Not completed. Adding an existing number leaves its time and status unchanged.
  • Any invalid input produces an error without changing records.

All four mastery check commands use the same INDEX and NUMBER rules. They preserve other student records and the current list filter. Changes are saved automatically and retained after restart. Run view id/INDEX to inspect the Number, Appointment time, and Status columns.

Example:

addmc id/1 num/2 dt/29-10|13:30, followed by view id/1, shows mastery check 2 at Oct 29, 13:30 as Not completed.

Deleting a mastery check: delmc

Removes a numbered mastery check appointment for a student, including its completion status.

Format: delmc id/INDEX num/NUMBER

  • INDEX must be a positive integer identifying a student in the currently displayed list, including find results.
  • NUMBER must be an integer from 1 to 2147483647, inclusive. Numbers are unique within each student's appointments.
  • Supply the id/ and num/ prefixes exactly once, in any letter case. Do not put text before the first prefix.
  • If the number is not registered for that student, the command reports that no changes were made.
  • Other mastery check appointments and the student remain in the address book.
  • Any invalid input produces an error without changing records.

Example:

delmc id/1 num/2 removes mastery check 2 from the first displayed student, if registered.

Marking a mastery check as completed: markmc

Marks an existing mastery check appointment as Completed without changing its appointment time.

Format: markmc id/INDEX num/NUMBER

  • INDEX must be a positive integer identifying a student in the currently displayed list, including find results.
  • NUMBER must be an integer from 1 to 2147483647, inclusive. Numbers are unique within each student's appointments.
  • Supply the id/ and num/ prefixes exactly once, in any letter case. Do not put text before the first prefix.
  • Marking an already completed mastery check reports that no changes were made.
  • Any invalid input produces an error without changing records.

Example:

markmc id/1 num/2, followed by view id/1, shows mastery check 2 as Completed.

Unmarking a mastery check as completed: unmarkmc

Changes an existing mastery check appointment's status to Not completed without deleting it or changing its time.

Format: unmarkmc id/INDEX num/NUMBER

  • INDEX must be a positive integer identifying a student in the currently displayed list, including find results.
  • NUMBER must be an integer from 1 to 2147483647, inclusive. Numbers are unique within each student's appointments.
  • Uses the same index, number, and registration rules as markmc.
  • Unmarking a mastery check that is already incomplete reports that no changes were made.
  • Any invalid input produces an error without changing records.

Example:

unmarkmc id/1 num/2, followed by view id/1, shows appointment 2 as Not completed.

Adding a mission: addmission

Creates one mission shared by all students. Adding a mission does not mark anyone as having submitted it; students without a submission record show Not submitted.

Format: addmission m/MISSION_ID n/NAME d/DEADLINE

  • Supply exactly one m/, n/, and d/ prefix, in any letter case and in either order. Do not put text before the first prefix. The command word is case-insensitive.
  • MISSION_ID must start with M followed by a positive integer of at least two digits, without unnecessary leading zeros. For example, M01, M02, and M105 are valid; M1 and M00 are not. The number must not exceed 9223372036854775807 (the largest supported value, with up to 19 digits). IDs must be unique among configured missions. Exceeding the limit reports the same mission-ID constraint message.
  • NAME must not be blank. Multiple words and ordinary punctuation are allowed. Leading and trailing whitespace is removed, and internal whitespace becomes a single space. Letter case and punctuation are preserved for display and saving.
  • Names are unique across the mission catalogue, ignoring case and whitespace differences. Rune Reading and rune reading are duplicates, even with different deadlines. Adding extra spaces before, after, or between the words also counts as the same name. RuneReading and Rune Reading! remain different names.
  • DEADLINE must be a real calendar date in YYYY-MM-DD format. For example, 2024-02-29 is valid but 2026-15-32 is not. Times and single-digit months or days are rejected. Past deadlines are accepted for recording existing assignments.
  • Choose the ID yourself; the application does not assign IDs automatically. Existing mission IDs do not change when another mission is deleted. A deleted ID can be chosen again afterward, but its previous submission records are removed and are not restored.
  • Successful additions are saved automatically. Invalid or duplicate additions do not change the catalogue or save the data file. Existing students and their list filter are preserved.

Examples:

  • addmission m/M01 n/Rune Reading d/2026-10-20
  • addmission d/2024-02-29 m/M105 n/Mission 1: Rune Reading! stores the name Mission 1: Rune Reading!.

The first example displays:

New mission added: M01 · Rune Reading (Due: 2026-10-20)

Missing IDs produce Specify a mission ID using m/MISSION_ID. Invalid IDs show the ID format constraint. Missing or blank names produce Provide a mission name using n/NAME. A valid name without a deadline produces Specify a deadline in YYYY-MM-DD format using d/DEADLINE. Unexpected text before the prefixes produces a format error with usage instructions. Repeated prefixes identify the repeated fields; invalid dates produce their respective constraint messages. An existing name produces This mission already exists in the mission list. An ID already used by a configured mission produces A mission with this ID already exists.

Deleting a mission: delmission

Format: delmission m/MISSION_ID

Example: delmission m/M03

Use exactly one m/ prefix, in any letter case. Mission IDs are case-insensitive, so m/m03 also identifies M03. Numeric-only values such as m/3 are rejected. Use the stable mission ID, not a student index or a position in the displayed list.

Deletion removes the mission and its submission records from every student, including students hidden by the current filter. Student details, studio records, and other missions are preserved. The current student filter stays active. The result area shows deletion feedback; run view id/INDEX to see the updated profile. Deletion is automatically saved and survives restart. The deleted ID can be explicitly reused by a later addmission command, but the old submission records are not restored. Unknown or invalid IDs leave data unchanged.

Recording a mission submission: markmission

Format: markmission id/INDEX m/MISSION_ID

  • INDEX identifies a student in the currently displayed list, including find results.
  • The index must be a positive integer without a sign or leading zeros.
  • MISSION_ID must identify a configured mission, for example M01 or M105.
  • Use the m/ prefix exactly once, in any letter case. Mission IDs are case-insensitive: m/m01 and m/M01 both identify M01. IDs are displayed and saved in uppercase.
  • Each mission ID identifies one configured assignment.
  • Repeated marking reports that the submission is already recorded and changes nothing.
  • Other students, other submissions, studio records, and the current student filter are preserved.
  • Records are maintained manually. Not submitted means no submission is recorded in AvengerHub.

Example: markmission id/1 m/M01, followed by view id/1, displays M01 as Submitted. An unknown mission ID or invalid command leaves existing records unchanged. Malformed arguments display an error with command usage. A positive index that does not identify a student in the currently displayed list is rejected during execution with an index error followed by the command's usage; check the current list and use an index shown there. The same applies to unmarkmission.

Removing a submission record: unmarkmission

Format: unmarkmission id/INDEX m/MISSION_ID

Uses the same index and mission ID rules as markmission. This removes only the selected student's submission record; it does not delete the student or the mission. Unmarking an unrecorded submission reports that no changes were made.

Example: unmarkmission id/1 m/M01, followed by view id/1, displays M01 as Not submitted.

The profile displays configured mission descriptions and deadlines. An empty catalogue shows “No missions configured.”

Editing a mission: editmission

Changes a shared mission's name, deadline, or both.

Format: editmission m/MISSION_ID [n/NAME] [d/DEADLINE]

  • Supply exactly one m/ prefix and an existing mission ID; prefix matching ignores letter case.
  • Supply at least one n/ or d/ prefix. Each may appear once.
  • Prefixes may appear in any order. Do not put text before the first prefix.
  • The command word and mission ID are case-insensitive.
  • Names and deadlines follow the same validation rules as addmission.
  • Omitted fields retain their existing values.
  • The new name must not duplicate another mission's name, ignoring case and whitespace differences. Keeping the mission's own name is allowed.
  • The mission ID, submission records, student details, and student filter remain unchanged.
  • Missions are shared: editing affects their displayed details for every student, including students hidden by the current filter.
  • An unchanged name and deadline produce no-change feedback.
  • Successful edits are saved automatically. Invalid edits leave records unchanged.
  • Run view id/INDEX again to inspect updated mission details.

Examples:

  • editmission m/M01 n/Rune Reading
  • editmission m/M01 d/2026-10-22
  • editmission m/M01 n/Rune Reading d/2026-10-22

Listing missions and submission statuses: listmissions

Lists mission summaries or student submission statuses, optionally filtered by mission ID and status.

Format: listmissions [m/MISSION_ID] [s/STATUS]

  • The command word, m/ prefix, and mission ID are case-insensitive.
  • Student records, submission records, mission definitions, and the current student filter remain unchanged.
  • Without either argument, displays all mission summaries with submission counts.
  • With m/MISSION_ID, displays statuses for that mission.
  • With s/submitted or s/overdue but no mission ID, displays matching submissions across all missions.
  • When both prefixes are supplied, applies the status filter to the selected mission.

Without a mission ID:

  • Lists all missions in ascending numeric ID order, showing each mission's ID, name, deadline, and submitted/total student count.
  • Submitted: X/Y means X of the Y currently displayed students have a recorded submission for that mission.
  • All missions remain visible regardless of the student filter, but counts include only currently displayed students.
  • An empty student list produces Submitted: 0/0.
  • Deadlines before the computer's current local date are labelled Deadline passed, even if every student has submitted. Missions due today are not labelled.
  • If no missions exist, displays No missions configured.

With m/MISSION_ID:

  • Supply exactly one m/ prefix and an existing mission ID.
  • Lists every currently displayed student's status for that mission, including their displayed index, name, and studio group.
  • A recorded submission is Submitted, regardless of the deadline.
  • A missing submission is Overdue when the deadline is before the computer's current local date; otherwise it is Not submitted. Missions due today are not overdue.
  • Students hidden by find are excluded.
  • Result numbers retain displayed student indexes. A result numbered 3 can therefore be inspected using view id/3.
  • An empty student list produces No students in the current student list.
  • Statuses reflect recorded submissions; an absent record does not confirm that a student has not actually submitted.
  • Optionally supply s/submitted or s/overdue to show only that status. Status values are case-insensitive, and m/ and s/ may appear in either order.
  • Supply each prefix at most once. Empty or unsupported status values are rejected.
  • If students are displayed but none match the status filter, reports No submissions match the selected status.

With s/STATUS only:

  • Each row represents one student–mission pair and includes the mission's ID, name, and deadline.
  • Rows are ordered by numeric mission ID, then displayed student order.
  • A student may appear more than once when multiple missions match. Their index always refers to the left student list.
  • Only currently displayed students are included. Records and the student filter remain unchanged.
  • If no missions exist, displays No missions configured.

Run list first to include all students in counts and status results. Rerun listmissions with the desired arguments to refresh its output.

Command results appear above the student panels. The results area grows with its content up to a height limit; scroll within it to read longer reports. Shorter feedback shrinks the area again, leaving more room for student details. Each new result starts at the top.

Examples:

  • listmissions displays all missions with submitted/total counts for the currently displayed students.
  • find g/1A, followed by listmissions m/M01, shows M01 statuses for the currently displayed students in studio group 1A.
  • listmissions m/M01 s/submitted lists recorded M01 submissions among currently displayed students.
  • listmissions m/M01 s/overdue lists currently displayed students missing M01 after its deadline.
  • listmissions s/submitted shows recorded submissions across all missions for currently displayed students.
  • listmissions s/overdue shows missing submissions whose deadlines have passed across all missions for currently displayed students.

Clearing all entries: clear

Clears all student records and the shared mission catalogue, including the students' associated studio records, notes, mastery checks, and submission records.

Format: clear

Exiting the program: exit

Exits the program.

Format: exit

Saving the data

AvengerHub automatically saves data after every successfully executed command. You do not need to save manually.

Mission submission marking and unmarking are saved automatically and retained when you reopen the application. Invalid mission commands leave existing records unchanged.

Editing the data file

AvengerHub's address book data is saved automatically as the JSON file data/addressbook.json, relative to the application's working directory (the directory from which it is launched). When following the Quick start instructions, this is the folder containing the JAR file. Advanced users can update data directly by editing that file.

Caution: Back up the file before editing it manually. If loading fails because of malformed JSON, invalid student details, or invalid mission catalogue data, AvengerHub logs the error and opens an empty address book. The entire dataset is rejected; no partial records are retained. Startup leaves the invalid file unchanged. The next successfully executed command, including list, overwrites that file with the current in-memory address book, which may be empty. Failed commands do not save. A missing file instead loads the sample data.

FAQ

Q: How do I transfer my data to another computer?
A: Install the app on the other computer and overwrite the data file it creates with the data file from your previous AvengerHub home folder.

Known issues

  1. When using multiple screens, if you move the application to a secondary screen, and later switch to using only the primary screen, the GUI will open off-screen. The remedy is to delete the preferences.json file created by the application before running the application again.
  2. If you minimize the Help Window and then run the help command (or use the Help menu, or the keyboard shortcut F1) again, the original Help Window will remain minimized, and no new Help Window will appear. The remedy is to manually restore the minimized Help Window.
